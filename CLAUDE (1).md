## What This Project Is

**MPG Church System** is a multi-tenant church management SaaS built for Seventh-day Adventist churches. Each church is an isolated tenant. The system manages: member records, households, departments, events, attendance, treasury (funds/inflows/outflows), announcements, leadership roles, approval workflows, and a full invite/onboarding pipeline.

**Three user tiers:**
- Platform admins → `/platform/...`
- Church operational staff (admins, pastors, clerks, etc.) → `/c/[churchSlug]/...`
- Regular church members → `/my/[churchSlug]`

## Access Guard System

All guards live in `src/features/access/queries.ts` (marked `server-only`).

| Guard | Protects | On failure |
|---|---|---|
| `requireUser()` | Any authenticated route | Redirects `/login` |
| `requireChurchAccess(slug)` | Church exists + user is member | Redirects `/create-church` |
| `requireChurchWorkspaceAccess(slug)` | Operational access | Redirects `/my/[slug]` or `/join/[slug]` |
| `requireMemberPortalAccess(slug)` | Member has `profile_id` link | Redirects to workspace or `/join/[slug]` |
| `requireChurchRole(slug, roles[])` | Specific role codes | Redirects to dashboard |
| `requirePlatformAdmin()` | Platform-level access | Redirects `/` |

`getUserAccessState(userId)` — the central aggregator, cached with React `cache()` per request.

`ChurchAccessContext` returned by all guards:
```ts
{
  userId, churchId, churchSlug, churchName,
  profile: { full_name, email, preferred_language, must_change_password },
  roles: string[],
  isPlatformAdmin: boolean,
  hasOperationalAccess: boolean,
  hasMemberLink: boolean,
}
```

## ⛔ NON-NEGOTIABLE RULES — Never Violate

### Access Control
- Every church workspace page calls `requireChurchWorkspaceAccess(slug)` as the **first line** of the page function. Never remove or move it.
- Every member portal page calls `requireMemberPortalAccess(slug)` as the **first line**. Never remove or move it.
- Platform admin pages call `requirePlatformAdmin()`. Never remove.
- Never check roles in client components — all authorization is server-side only.
- `isPlatformAdmin` bypasses all church-level role checks.

### Server Actions
- All mutations are Server Actions (`"use server"`). Never write to Supabase from client code.
- All Server Actions return `{ ok: true; ... } | { ok: false; error: string }`. Never throw to client.
- Always call `revalidatePath()` after mutations that affect displayed data.
- Extract form values with `getString()` / `getNullableString()` helpers — never inline `formData.get()` throughout the action.

### Forms
- Never rename form input `name=""` attributes. Server actions read them by name. Renaming breaks the action.
- Never change a Server Action's function signature without checking all callers.

### Database Lifecycle Rules
- **Never set `portal_joined_at`** anywhere except `completeFirstLoginPasswordChangeAction` in `src/features/member-portal/actions.ts`. This is the only place. Not in RPCs, not in onboarding actions, not in invite claim actions.
- `must_change_password` on `profiles` gates the first-login password screen. Never bypass this check.
- `.maybeSingle()` when a row may not exist. Never `.single()` (throws on no rows).
- Privileged multi-table writes go through Supabase RPC functions, not chained inserts.

### Invite Claim
- After invite claim RPC: always verify `status === "claimed"`, `claimed_at` is set, `claimed_by_user_id` is set. Fail explicitly if any is missing.
- Token generation uses `crypto.randomBytes(24).toString("hex")` only. Never `Math.random()`.
- Always check for an existing pending invite before creating a new one.

### Routing
- Post-login destination is always determined by `resolvePostAuthDestination()` in `src/features/access/queries.ts`. Never hardcode redirect destinations after login.
- After invite claim with session: redirect `/my/[slug]?tab=overview&onboarding=1`
- After invite claim without session: redirect `/login?registered=1&church=[slug]`
- After public join with session: redirect `/my/[slug]?tab=overview`
- Validate `?redirect=` params: only accept paths starting with `/` and not `//`.

### TypeScript
- Strict mode is on — no implicit any, no loose nulls.
- Always use `@/` path alias, never relative `../../` imports.
- Type discriminated unions for action results: always check `ok` before accessing typed fields.

## Database Schema (Key Tables)

### Core
- `profiles` — mirrors auth.users. Has `must_change_password` (not in database.ts — never remove from `ProfileRow` local type)
- `churches` — tenant root. `slug` used in all URLs.
- `church_users` — join table: user ↔ church. `status: active|inactive|invited`
- `church_role_assignments` — operational roles per user per church. `is_active` must be true.
- `platform_role_assignments` — `platform_owner|platform_admin|platform_support`

### Members
- `members` — core member record. `profile_id` links to auth user. `portal_invited_at` / `portal_joined_at` lifecycle columns.
- `member_departments` — member ↔ department many-to-many. `department_name` is denormalized at insert.
- `member_onboarding_invites` — invite tokens. `status: pending|claimed|revoked|expired`
- `member_status_history` — audit log of status changes

### Other
- `households`, `church_departments`, `church_events`, `church_announcements`
- `approval_requests` / `approval_steps` / `approval_policies`
- `treasury_funds` / `treasury_inflows` / `treasury_outflows`
- `church_access_requests` / `department_leadership_requests`
- `church_notifications` / `platform_notifications`

- `church_permission_assignments`

## RPC Functions (External — No SQL in This Repo)

All 5 RPCs live in the Supabase project dashboard. There are no `.sql` files here.

| RPC | Called from | What it does |
|---|---|---|
| `create_church_with_owner(...)` | `features/churches/actions.ts` | Creates church + assigns creator as church_admin |
| `complete_member_onboarding(...)` | `features/member-onboarding/actions.ts` | Public join: links/creates member, creates church_users |
| `complete_member_onboarding_from_invite(...)` | `features/member-invite/actions.ts` | Existing-member invite claim: marks invite claimed, links user |
| `complete_open_member_onboarding_from_invite(...)` | `features/member-invite/actions.ts` | Open invite: creates new member row, marks invite claimed |
| `complete_first_login_security(p_user_id)` | `features/member-portal/actions.ts` | Clears `must_change_password` on profiles |

**Critical invariant:** None of these RPCs set `portal_joined_at`. If asked to modify onboarding logic, always tell the developer what the RPC needs to do differently — they update it manually in Supabase.

## Known Fragile Areas — Always Flag Before Touching

### 1. Invite Claim Race Condition
`supabase.auth.signUp()` succeeds but the RPC fails → orphaned auth account with no `church_users` or `members` link. No rollback exists. Flag this risk whenever touching `src/features/member-invite/actions.ts`.

### 2. Open Invite Email Deduplication
`eq("email", null)` does not match NULL rows in Postgres. Multiple null-email open invites can be created. Do not "fix" this without understanding the implication.

### 3. `member_departments.department_name` Denormalization
Written at insert time. Not updated if a department is renamed. Do not add rename logic without also updating all `member_departments` rows.

### 4. `must_change_password` Not in database.ts
Queried as a local `ProfileRow` type in `src/features/access/queries.ts`. Will be wiped if `database.ts` is regenerated carelessly.

### 5. `MemberInviteButton` Functional Bug (Pre-Fix)
Before Pack 12 of the Phase 2 refactor is applied: `MemberInviteButton` in `MembersWorkspaceUnified.tsx` does not call `createMemberInviteAction`. It constructs a URL client-side without creating a DB row. This is a known bug — do not copy this pattern.

### 6. Two Overlapping Access Systems
`church_role_assignments` (role-based) and `church_permission_assignments` (explicit permissions) both exist. The only permission actively checked in code is `access_control`. Do not assume roles automatically grant permissions.

## PostgREST Join Normalization

PostgREST joins can return a single object OR a single-element array. Always normalize before accessing:

```ts
// BAD — crashes if PostgREST returns an array
const name = row.church.name;

// GOOD — normalize first (see pattern in src/features/access/queries.ts ~line 98)
const church = Array.isArray(row.church) ? row.church[0] : row.church;
const name = church?.name;
```

## Multi-Church Edge Case

A user can belong to multiple churches. The member portal only shows one church at a time. `resolvePostAuthDestination()` picks the primary church via `pickPrimaryChurch()`. Never build features that assume exactly one church per user.
